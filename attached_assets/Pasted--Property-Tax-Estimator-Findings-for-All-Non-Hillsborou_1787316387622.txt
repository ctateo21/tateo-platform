# Property Tax Estimator — Findings for All Non-Hillsborough Counties

Companion to HILLSBOROUGH_TAX_FIX_SPEC.md. Investigated live against the
actual `server/routes.ts`, `server/integrations/county-parcel-lookup.ts`,
and `server/integrations/tax-bill-scraper.ts` on 2026-08-20.

## Headline finding
The P1 status table said Lee County was "confirmed" via ArcGIS and Pinellas
had its `pcpao.gov tax_estimatorout` flow "cracked and matching exactly."
**Neither is true of the code currently live in `routes.ts`.** Lee is
explicitly grouped with the formula-only counties (line 709 comment:
`"Sarasota, Hernando, Lee, Collier, Polk use a formula estimate"`), and the
`tax_estimatorout` endpoint doesn't appear anywhere in the codebase — only
a comment mentioning `(pcpao.gov)`. That work either never got merged or
was lost. Worth checking Replit's history/checkpoints for it before
rebuilding from scratch.

## BUG 1 (shared with Hillsborough): street-truncation + city-only validation
**Files:** `county-parcel-lookup.ts` → `streetForQuery()`, used by
`lookupPinellasParcel()` and `lookupManateeParcel()`

Identical bug to Hillsborough's `streetForSearch()` — same 3-token
truncation, same city-only match validation (`SITE_CITYZIP.includes(inputCity)`
/ `SITUS_POSTAL_CITY.includes(inputCity)`), no street-name check. Any
Pinellas or Manatee address on a multi-word or directional street is at
the same risk of silently resolving to the wrong parcel that I proved live
for Hillsborough's Bay to Bay Blvd case.

**Fix:** Same as Hillsborough Bug 1 — don't truncate to a fixed token
count, validate the returned street name (not just city) before accepting
a match. Since this exact bug is now duplicated three times across three
files, worth extracting one shared `resolveStreetCandidate()` utility used
by all three lookups instead of three independent copies that can each
drift or be fixed inconsistently.

## BUG 2 (Pinellas/Pasco): fallback silently mislabeled as live
**File:** `routes.ts`, the `/api/property-tax/county` handler

`source` is hardcoded to `` `${county}-api` `` any time the code enters the
Pinellas/Pasco branch at all — regardless of whether `pinellasAdValorem`
actually resolved from the bill scrape or fell through to the flat
`adValorem`. There is currently no way — not in the API response, not in
the UI if it surfaces `source` — to tell a real Pinellas number from an
approximated one.

**Fix:** Set `source` based on what actually happened:
`"pinellas-bill-derived"` when `pinellasAdValorem !== null`,
`"pinellas-formula-fallback"` otherwise (same idea for Pasco, which should
just always report `"pasco-formula-fallback"` until it has its own
bill-derived path). This costs nothing to implement and immediately makes
it possible to audit, county by county, what fraction of live estimates
are actually live.

## BUG 4 (all counties): silent scrape disablement
**File:** `tax-bill-scraper.ts`, line ~163

If `APIFY_TOKEN` isn't set in the live Replit environment, every CDD/
non-ad-valorem scrape (Hillsborough included) silently no-ops with just a
`console.log` — no error surfaced anywhere the user or you would see it.
**Action:** confirm `APIFY_TOKEN` is actually set in the live deployment's
environment (not just your local `.env`), and consider upgrading this from
a `console.log` to something that surfaces in whatever monitoring/logging
you actually check, since a missing token silently degrades every county
at once.
